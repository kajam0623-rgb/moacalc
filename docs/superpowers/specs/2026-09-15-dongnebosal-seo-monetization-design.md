## 5. 수익화

### 5.1 승인 가능성
운신(`unsin.co.kr`)이 사주 결과 페이지에 애드센스를 달고 있음이 스크린샷으로 확인됨 → 이 카테고리는 승인됩니다.

### 5.2 신청 전 선결 과제
**`moacalc.vercel.app`이 구 브랜드 내용을 서빙 중.** 같은 콘텐츠를 두 도메인이 내보내면 심사에 불리합니다. Vercel CLI로는 관리가 안 되며(`alias set` → "already in use", `alias rm` → "not found", `domains inspect` → "no access") 대시보드에서만 처리 가능합니다.

### 5.3 코드 작업
`build_site.js:15`의 `ADSENSE_CLIENT` 한 줄만 채우면 `headExtra`의 로더(`build_site.js:822`)와 `adSlot()`이 자동으로 붙습니다. **추가 코드 0.**

### 5.4 광고 배치 (승인 후)
| 위치 | 형식 | 상태 |
|---|---|---|
| 결과 아래 | 디스플레이 자동 | `adSlot()` 이미 존재 |
| 본문 중간 | 인아티클 | 신규 |
| 하단 고정 | 앵커/오버레이 | 애드센스 자동광고로 켜면 코드 0 |

### 5.5 공유
현재 0. 포스텔러·운신 둘 다 있음.

- **Web Share API (`navigator.share`) + URL 복사** — 앱키 불필요, 즉시 가능
- 공유 문구에 결과 요약을 담고 **URL은 도구 페이지 그대로**
  > "내 일간은 임수(壬水), 오행은 수가 50%로 과다래. 너도 해봐 → dongnebosal.com/saju.html"
- **생년월일을 URL 쿼리에 넣지 않습니다.** 개인정보가 링크를 타고 퍼지고, 쿼리 URL이 색인되면 canonical 문제도 생깁니다
- 카카오 공유는 카카오 개발자 앱키가 필요(사용자 작업). 자리만 비워둡니다

### 5.6 수익 추정 — 추정입니다
한국 애드센스 RPM은 운세·생활 대략 1,000~2,500원/1000PV, 금융·부동산·세금 3,000원 이상으로 알려져 있습니다. 계산기 30종이 금융·세금이라 혼합 RPM은 유리한 편입니다.

RPM 2,000원 가정 → 월 100만원 = 월 50만 PV = 일 1.7만.

**466페이지로 바로 닿지 않습니다.** 색인·순위에 3~6개월이 걸리고, 첫 성과는 월 5~20만원 구간일 가능성이 높습니다. 50~100만원은 이 확장을 2~3차까지 돌리고 1년 가까이 봐야 하는 숫자입니다. 3개월 뒤 20만원을 실패로 읽지 않기 위해 미리 적어둡니다.

애드센스 심사는 수 주가 걸리므로 **1단계와 병렬로 신청**합니다.

### 구현 계획 분할
6단계 전부를 한 계획으로 묶지 않습니다. 원고 생성 분량이 크고, 각 단계의 중복 게이트 결과에 따라 다음 단계의 원고 전략이 바뀌기 때문입니다.

- **1차 계획: 1~3단계** (계측·공유 → 월력 132 → 일주 60)
- 2차 계획은 1차의 게이트 수치를 보고 작성합니다. 월력과 일주의 실제 유사도가 기준을 어떻게 통과하는지가 띠궁합 78의 원고 설계를 좌우합니다.

## 7. 검증 게이트

매 단계 전부 통과해야 배포합니다.

1. **`node verify.js`** — 197개 전부 통과 (빌드가 자동으로 막음)
2. **중복 게이트** — 3-gram 자카드 전수 비교. **전 페이지 공통 3-gram(= 네비·푸터·FAQ 같은 보일러플레이트)을 뺀 뒤** 잰다: 평균 40% 미만, 최대 70% 미만
   - 기준 근거: 기존 일진 60을 전수로 재측정했더니 크롬 제거 후 **평균 12.3%, 최대 47.9%**였다 (`tools/gate.js`)

   > **이 항목의 앞 판은 틀렸었다.** 처음에는 "평균 67.8%, 최대 73.2%"라고 적었는데, 그 수치는 이전 세션이 **60개 중 8개만 표본으로** 재서 나온 값이었다. 전수로 재면 최대가 **84.8%**(경진↔경술)이고, 최악 쌍이 그 8개 표본에 아예 없었다. 음력을 명절 21개로만 검증하고 "정확하다"고 결론 냈다가 전수 감사에서 3.692% 불일치가 나온 것과 같은 표본 편향이다.
   >
   > 더 중요한 사실도 함께 드러났다. **전 페이지 공통 3-gram이 문서당 평균의 76.4%**다. 보일러플레이트를 포함해 재면 어떤 페이지군이든 68~85% 구간에 몰려 게이트에 변별력이 없다. 그래서 공통 크롬을 뺀 뒤 재는 방식으로 바꿨다. 셀렉터를 하드코딩하지 않고 그룹 안에서 "모든 문서에 다 있는 3-gram"을 찾아 빼므로 페이지군이 바뀌어도 따로 손댈 필요가 없다.
   - 넘으면 배포 중단하고 원고를 더 갈라냄
3. **얇은 콘텐츠 게이트** — 페이지당 크롤러 본문 2,000자 이상
4. **라이브 확인** — 실제 URL 200 + 본문이 실제로 렌더되는지

### 측정 자체를 먼저 의심한다
지난 세션에 측정 오류를 제품 결함으로 오독한 사례가 3건 있었습니다.
- `file://` CORS로 `cssRules` 접근 불가 → "매칭 규칙 0건"
- Browser pane이 뷰포트를 0으로 보고 → 스크린샷 전부 검은 화면
- `gunghap:`이 `stargunghap:`의 부분문자열이라 엉뚱한 맵을 읽음

게이트는 자동 스크립트로 돌리고, 숫자가 이상하면 제품보다 측정을 먼저 의심합니다.
